# GameTimer — project retrospective (November 2026)

A whole-system review at v2.0.0-rc1 (master after PR #61): security, architecture, code validity, and a
critical look at the product and its decisions. Written by a different model (Fable 5.2) than the one that
built the project (Opus 5.5). No code was changed. Russian translation below.

> **Follow-up (2026-11-15).** Fixed after this review: S1 (state files: registry marks, deletion and old
> copies are reported), S3 (new apps are reported, protocol minor 6), S7 (actions pinned by commit), S11 and
> the positioning in the README (P1, P3). The rest is tracked in `.agent/ROADMAP.md`. The text below is the
> review as written.

## Scope and method

- **Read in full:** the C# Noise implementation, C# pairing, the Windows state protection (`ProtectedStore`,
  `UsageTracker`, `SettingsService`, `TimerStateStore`, `SessionLog`), `ProcessProtection`, the parent
  authentication gate, setup signals, the embedded server setup and `NetworkFilter`, the relay options, the
  child app's `ParentPin`, both Android manifests, all CI workflows, `docs/SECURITY.md`, `docs/PRIVACY.md`,
  protocol §8, §10, §11. The phone's rules (`PlayBackend`) and the child app were reviewed closely during C3–C4.
- **Sampled, not read line by line:** `MainWindow.xaml.cs`, `TimerController`, the relay internals, the Kotlin
  hub client and the parent app UI, mDNS discovery.
- **Nothing was run on a device.** Each finding says whether it was confirmed in the code or is reasoning that
  still needs a test.

## Summary

1. **The network side is strong; the local side is weak, and the documentation says otherwise.** Pairing, the
   Noise sessions and the relay design hold up. The enforcement on the PC is defeated by deleting one file,
   changing the clock or removing a shortcut — by the child at the keyboard, who is the real adversary.
2. **The effort went to the unlikely attacker.** Route rotation, eviction pools and a typed pairing code defend
   against outsiders on the network. The next investment should be local enforcement on Windows.
3. **The Windows app — the most used part — has no automated tests**, while the protocol has 150 and the
   phone's rules 30+.
4. **The phone agent is the weakest product promise.** Without Device Owner it is a cooperative tool; newly
   installed games are not limited and nobody is told.
5. **The process worked** (spec first, test vectors, interop tests in CI, a review per PR), but reviews were
   scoped to diffs, so old PC-side gaps survived many reviews.

## Security findings

Severity is relative to the product's own claims and its stated adversary (a child using the PC or phone).

### High

**S1. The PC's "tamper-resistant" state files can be reset by deleting them.** Confirmed in the code.
- `ProtectedStore.Read` returns "no file" without a tamper report when the file is missing, even if its `.bak`
  is there. `UsageTracker` then starts with 0 seconds used; `SettingsService` falls back to defaults (schedule
  off, phone control off).
- With the `.bak` deleted, a **plaintext** `settings.json`, `usage.json` or `timer-state.json` is accepted as a
  "legacy migration" (the path kept for updates from v1.5).
- The files are read at start, so it needs a restart of the app: a reboot or logoff is enough. If no timer is
  running at that moment (e.g. after the allowance ran out), nothing is recorded.
- `docs/SECURITY.md` says this design "defeats the realistic case — a child editing a file to reset today's
  used time". Deleting is easier than editing.
- Direction: remove the plaintext path (the migration is long done); keep a "state exists" marker elsewhere
  (e.g. a DPAPI value in HKCU with a counter) so a missing or older file is tampering; report it.

**S2. The PC's schedule trusts the wall clock.** Confirmed in the code.
- `UsageTracker.Today()` and `ScheduleEvaluator.Evaluate(DateTime.Now, …)`: moving the date forward gives a
  fresh daily allowance; moving the time moves into the allowed hours. After a reboot a running timer resumes
  by the wall-clock target, so setting the clock back adds time.
- Nothing is reported to the parents (the phone agent reports clock changes since C4; the PC does not).
- It needs the right to change the clock: the child has it in the owner's own set-up (one administrator
  account, decision D6); a standard account does not.
- Direction: port the phone's design (days on the monotonic clock, a day stored as an instant, the relay's or
  a parent's time as a check, `clockChanged` events) — ideally as shared, tested rules rather than a second copy.

**S3. On the child's phone a newly installed game is not limited, and the parents are not told.** Confirmed:
nothing listens for app installs. The model is "limit what the parent ticked", so it fails open for anything
new. Direction: a `newApp` history event with a notification, and an option "limit new apps until I decide".

### Medium

**S4. Both agents fail open when they are not running.** The Windows app starts from a shortcut in the user's
Startup folder: deleting it, or disabling it in Task Manager, means no enforcement after the next reboot. The
parent app shows the PC as offline and nothing else (same on the phone, by the owner's decision in C4).
Direction: a scheduled task or service on Windows; in the parent app, an optional "not seen since …" notice
for a device that was online daily.

**S5. "Protection from closing" does not stop suspending the process.** By reading the code, not tested: the
deny rule covers only `PROCESS_TERMINATE`; the same user keeps `PROCESS_SUSPEND_RESUME` (Resource Monitor →
Suspend) and can rewrite the rule as the process owner. A suspended app enforces nothing and logs nothing
until resumed.

**S6. The PC's history is a plaintext file** (`sessions.jsonl`): "closed" and "tampered" entries can be
deleted. Notifications already delivered to the parents' phones are the only durable record.

**S7. The release pipeline pins third-party actions by tag, not by commit**, in the job that holds the APK
signing key (`gradle/actions/setup-gradle@v4`, `actions/setup-java@v4`, …) and in the job with write access
(`softprops/action-gh-release@v2`). The deploy workflow already pins commits. There is no Gradle dependency
verification and no NuGet lock file. A compromised action tag could sign or publish a malicious build.

**S8. The relay is an open, unauthenticated pipe with no byte budget**, on one machine, with its address
compiled into every app. Anyone who implements the framing can use it as a free tunnel (cost, capacity: 400
agent sockets); if it goes away, "from anywhere" stops for every install until an app update. Child phones now
hold a permanent socket each. Direction: a per-socket byte budget, alerts, a configurable relay address and a
short self-hosting note.

**S9. Not covered on the phone** (reasoning; some are documented already): a second Android user or guest
profile, work profile / dual apps, browser games, safe mode, and — with strict mode off — "Clear data" or
uninstall, which look like "offline".

### Low

- **S10.** The Windows password fallback (`LogonUser`) locks for 30 s after 3 wrong tries, in memory only: a
  restart resets it. Whether an account with a blank password passes was not tested.
- **S11.** `docs/SECURITY.md` calls updates "a signed GitHub Release". The APKs are signed; the Windows
  installer is not code-signed. Correct the text or sign the installer.
- **S12.** The child app trusts the relay's `Date` header through TLS. Check on a device that a
  user-installed certificate authority is not trusted by the Ktor CIO client (the platform default should
  exclude it).
- **S13.** Strict mode's guard is a heuristic (the app's name on a settings screen). It needs a test matrix
  across vendors; expect both misses and false closes.
- **S14.** State files live next to the exe (`AppContext.BaseDirectory`) instead of the user's data folder.

### Checked and sound

- **Noise.** Hand-written in C# and Kotlin, but both are checked against published vectors (cacophony, snow)
  and against each other in CI; nonce exhaustion, all-zero DH results and message sizes are handled.
- **Pairing.** A one-time secret in the QR, a typed 6-digit code bound to the handshake, Windows Hello, and
  "two phones used this code" detection. Check-and-commit is one critical section. I found no way for a second
  phone to slip in.
- **Server surface.** Two WebSocket paths, browsers refused, LAN addresses only, unknown keys closed silently.
- **Relay design.** It cannot read or forge anything; route claims can be dialled but not registered without
  the secret; the agent keeps its own limits whatever the relay sends.
- **Android.** No exported components beyond the launcher and system-bound receivers; backups off; keys sealed
  with the Keystore; the parent PIN uses PBKDF2 with a lockout that survives reboots.
- **Release key.** Available only to `v*` tags through a GitHub environment (the owner confirmed the setting).

## Architecture and code validity

**A1. No tests for the Windows app's logic.** All 152 C# tests cover the protocol and the relay.
`TimerController` (657 lines), `ScheduleEvaluator`, `UsageTracker`, `ProtectedStore` and the mapping from
protocol requests to the timer have none. S1 and S2 are exactly what such tests would have exposed.

**A2. `MainWindow.xaml.cs` is 2,578 lines of code-behind.** No view models; static helpers hold state
(`ProtectedStore`, `PasswordHelper`). Many `catch { }` blocks swallow failures: a settings save that fails is
silent. It works, but every change there is risky and untestable.

**A3. Everything exists twice, and the copies have diverged.** The protocol is implemented in C# and Kotlin
(reasonable: vectors and interop tests keep them aligned). The *rules* are also implemented twice
(`ScheduleEvaluator` / `TimerController` vs `ScheduleRules` / `PlayBackend`) and now differ: clock hardening,
grants past the schedule, tamper events and queued wake-ups exist only on the phone side. Options:
1. Keep two code bases, add shared rule vectors (as for the protocol). Cheapest.
2. Move the rules and protocol into one core (Rust with `snow`, or Kotlin/Native) with thin bindings. Pays off
   only if iOS or more platforms come.

**A4. `PlayBackend` (889 lines) was shaped by review patches.** Day anchoring with three trust levels plus
`lift` / `auto` / `bonus` flags is correct per its tests, but hard to reason about. Extract a pure day clock and
a budget, and test them against a simple reference model with random operation sequences.

**A5. Protocol growth.** Six minor versions (0–5) since v1.7.0 and a 789-line spec. Capability and minor
negotiation are done well. The relay part (pools, eviction, route rotation) is heavy for the number of users,
and every addition costs two implementations.

**A6. No update path.** Neither the Windows app nor the sideloaded APKs learn about new versions, so security
fixes reach nobody automatically. A "new version available" check against GitHub releases would help (it is a
small privacy trade-off; make it optional).

**A7. No field visibility.** No telemetry by design, so failures in the field are invisible. An "export
diagnostics" button would keep the privacy stance and still make support possible.

## The product, critically

**P1. Positioning.** Operating-system tools (Microsoft Family Safety, Google Family Link, Apple Screen Time)
enforce inside the OS and fail closed. A user-space app cannot match that. GameTimer's real strengths are
different: no accounts and no cloud, it works with one shared Windows account, a visible countdown the child
can see, one parent app for PC and phone, end-to-end encryption, open source. The honest position is a
**transparent timer for a family that has an agreement**, not unbreakable control. The README should say so.

**P2. The threat model is inverted.** The outsider on the network faces bank-grade cryptography. The child at
the keyboard faces a deletable file. Decision D6 (one shared administrator account) is the root: almost every
local finding above follows from it. The "known gap" in protocol §11 — a Windows service plus a standard child
account, with an in-app parent PIN — is the single change that would make PC enforcement real.

**P3. Phase C promises more than Android allows.** Without Device Owner the agent can be removed, cleared or
side-stepped, and Android's direction (restricted settings for sideloaded apps, accessibility policy,
developer verification in 2027) works against it. Alternatives:
- label the phone agent **beta** in v2.0 and describe it as cooperative;
- recommend Family Link for hard enforcement and keep GameTimer Child for the shared view and "ask for more time";
- offer Device Owner set-up as an advanced option for a dedicated child's device.

**P4. Two mental models.** On the PC the timer counts all time and locks the computer; on the phone it counts
only chosen games. Parents see both in one app. Either add a "games only" mode on the PC (by foreground
process) or state the difference clearly in the app.

**P5. Platform gaps.** No iOS parent app (many parents have iPhones), no iOS child, no consoles. The shared
Kotlin module already builds for iOS, so the parent app is the natural next platform.

**P6. Sustainability.** One maintainer; the relay, Firebase and the signing key are personal; no human code
review and no external audit. That is fine for a family tool and should limit what is claimed publicly.

## What went well

- Specification first, with independent test vectors and C# ↔ Kotlin interop tests in CI.
- An independent review on every PR found real defects each time (five passes for C3, three for C4).
- Decisions were recorded with dates and reasons; the privacy position is consistent and documented.
- Release hygiene: the signing key is scoped to tags; release candidates before a release.

## What to change in the process

- **Threat model before code** for security-relevant steps. In C3–C4 the clock problem was found one exploit
  at a time across eight review passes; a one-page model up front would have found most of it.
- **Whole-system reviews at milestones**, not only diff reviews. The PC gaps (S1, S2) date from v1.5–v1.6.
- **Test on devices per step.** C2, C3 and C4 all reached a release candidate without a device session.
- **Smaller PRs.** C3 and C4 each changed about a thousand lines of security logic at once.
- **A reviewer that differs from the author** (another model, or a human for the risky parts).

## Proposals, in order

**Before v2.0 final**
1. Correct `docs/SECURITY.md` (S1, S11) and state the cooperative positioning in the README (P1, P3).
2. Close S1 cheaply: drop the plaintext path, treat a missing state file as tampering.
3. Notify parents about a newly installed app on the child's phone (S3).
4. Pin actions by commit in `release.yml` (S7).
5. Run the device session (`child/README.md` steps 1–10).

**Next**
6. PC clock hardening and clock events (S2), built on rules shared with the phone (A3).
7. Tests for `TimerController`, the schedule and the state store (A1).
8. Start the Windows app from a scheduled task; protect or chain the history (S4, S6).
9. Relay: byte budget, alerts, configurable address (S8).

**Strategic**
10. Windows service + standard child account + in-app parent PIN (P2).
11. An iOS parent app (P5).
12. An update check (A6); optional Device Owner mode (P3).

# GameTimer — ретроспектива проекта (ноябрь 2026), перевод

Обзор всей системы на версии v2.0.0-rc1 (master после PR #61): безопасность, архитектура, корректность кода и
критический взгляд на продукт и принятые решения. Писала другая модель (Fable 5.2), не та, что делала проект
(Opus 5.5). Код не менялся.

> **Что сделано после обзора (15.11.2026).** Исправлено: S1 (файлы состояния: отметки в реестре, удаление и
> подкладывание старых копий теперь видны), S3 (о новых приложениях сообщается, minor 6 протокола), S7
> (действия CI закреплены по коммитам), S11 и позиционирование в README (P1, P3). Остальное отслеживается в
> `.agent/ROADMAP.md`. Ниже — текст обзора как он был написан.

## Охват и метод

- **Прочитано полностью:** реализация Noise на C#, подключение телефона (C#), защита файлов состояния Windows
  (`ProtectedStore`, `UsageTracker`, `SettingsService`, `TimerStateStore`, `SessionLog`), `ProcessProtection`,
  проверка родителя, сигналы установщика, настройка встроенного сервера и `NetworkFilter`, параметры relay,
  `ParentPin` детского приложения, оба манифеста Android, все сценарии CI, `docs/SECURITY.md`,
  `docs/PRIVACY.md`, протокол §8, §10, §11. Правила телефона (`PlayBackend`) и детское приложение подробно
  разбирались в C3–C4.
- **Просмотрено выборочно:** `MainWindow.xaml.cs`, `TimerController`, внутренности relay, клиент на Kotlin и
  интерфейс родительского приложения, обнаружение в сети (mDNS).
- **На устройствах ничего не запускалось.** У каждой находки указано, подтверждена ли она по коду или это
  рассуждение, которое ещё нужно проверить.

## Главное

1. **Сетевая часть сильная, локальная слабая, а документация утверждает обратное.** Подключение, сессии Noise
   и устройство relay выдерживают проверку. Ограничения на ПК снимаются удалением одного файла, переводом
   часов или удалением ярлыка — это делает ребёнок за клавиатурой, то есть настоящий противник.
2. **Силы ушли на маловероятного противника.** Смена маршрутов, пулы с вытеснением и вводимый код защищают от
   посторонних в сети. Следующее вложение должно быть в локальную защиту на Windows.
3. **У приложения Windows, самой используемой части, нет автоматических тестов**, при том что у протокола их
   150, а у правил телефона больше 30.
4. **Агент на телефоне — самое слабое обещание продукта.** Без Device Owner это инструмент для договорённости;
   новые установленные игры не ограничиваются, и никто об этом не узнаёт.
5. **Процесс сработал** (сначала спецификация, тестовые векторы, тесты совместимости в CI, ревью на каждый
   PR), но ревью смотрели только изменения, поэтому старые дыры на ПК пережили много ревью.

## Находки по безопасности

Серьёзность дана относительно обещаний самого продукта и его противника (ребёнок за ПК или с телефоном).

### Высокая

**S1. «Защищённые» файлы состояния на ПК сбрасываются удалением.** Подтверждено по коду.
- `ProtectedStore.Read` при отсутствии файла возвращает «файла нет» без записи о вмешательстве, даже если
  рядом лежит `.bak`. `UsageTracker` тогда начинает с 0 секунд, `SettingsService` берёт значения по умолчанию
  (расписание выключено, управление с телефона выключено).
- Если удалить и `.bak`, **незашифрованный** `settings.json`, `usage.json` или `timer-state.json` принимается
  как «перенос со старой версии» (путь остался для обновления с v1.5).
- Файлы читаются при запуске, поэтому нужен перезапуск приложения: хватит перезагрузки или выхода из системы.
  Если таймер в этот момент не идёт (например, лимит уже исчерпан), ничего не записывается.
- В `docs/SECURITY.md` сказано, что эта защита «закрывает реальный случай — ребёнок правит файл, чтобы
  сбросить использованное время». Удалить проще, чем править.
- Что делать: убрать путь с незашифрованным файлом (перенос давно состоялся); хранить отметку «состояние
  есть» в другом месте (например, значение DPAPI в HKCU со счётчиком), чтобы пропавший или старый файл
  считался вмешательством; сообщать о нём.

**S2. Расписание на ПК верит системным часам.** Подтверждено по коду.
- `UsageTracker.Today()` и `ScheduleEvaluator.Evaluate(DateTime.Now, …)`: перевод даты вперёд даёт новый
  дневной лимит, перевод времени — попадание в разрешённые часы. После перезагрузки идущий таймер
  продолжается по системному времени окончания, так что перевод часов назад добавляет время.
- Родителям ничего не сообщается (агент на телефоне сообщает о смене часов с C4, ПК — нет).
- Нужны права менять часы: у ребёнка они есть в твоей собственной конфигурации (одна учётная запись
  администратора, решение D6); у стандартной учётной записи их нет.
- Что делать: перенести решение с телефона (дни по монотонным часам, день как момент времени, сверка со
  временем relay или родителя, события `clockChanged`) — лучше общими, покрытыми тестами правилами, а не
  второй копией.

**S3. На телефоне ребёнка новая установленная игра не ограничена, и родителям не сообщают.** Подтверждено:
установку приложений никто не отслеживает. Модель «ограничиваем то, что отметил родитель» пропускает всё
новое. Что делать: событие `newApp` в истории с уведомлением и настройка «ограничивать новые приложения, пока
я не решу».

### Средняя

**S4. Оба агента ничего не ограничивают, когда не запущены.** Приложение Windows стартует с ярлыка в папке
автозагрузки пользователя: удалить его или отключить в диспетчере задач — и после перезагрузки ограничений
нет. Родительское приложение показывает ПК «не в сети», и только (на телефоне так же, по твоему решению в C4).
Что делать: запуск через планировщик задач или службу; в родительском приложении — необязательное
предупреждение «не на связи с …» для устройства, которое бывало в сети каждый день.

**S5. «Защита от закрытия» не мешает приостановить процесс.** По чтению кода, не проверено: запрет касается
только `PROCESS_TERMINATE`; у того же пользователя остаётся `PROCESS_SUSPEND_RESUME` (Монитор ресурсов →
«Приостановить»), и как владелец процесса он может переписать запрет. Приостановленное приложение ничего не
ограничивает и ничего не записывает, пока его не возобновят.

**S6. История на ПК — обычный текстовый файл** (`sessions.jsonl`): записи «закрыли» и «вмешательство» можно
удалить. Единственный надёжный след — уведомления, уже дошедшие до телефонов родителей.

**S7. Сценарий релиза закрепляет сторонние действия по тегу, а не по коммиту**, причём в задаче с ключом
подписи APK (`gradle/actions/setup-gradle@v4`, `actions/setup-java@v4`, …) и в задаче с правом записи
(`softprops/action-gh-release@v2`). Сценарий выкладки relay уже закреплён по коммитам. Проверки зависимостей
Gradle и файла блокировки NuGet нет. Подменённый тег действия мог бы подписать или опубликовать вредоносную
сборку.

**S8. Relay — открытый канал без авторизации и без лимита трафика**, на одной машине, с адресом, вшитым в
каждое приложение. Любой, кто реализует формат кадров, может использовать его как бесплатный туннель
(расходы, ёмкость: 400 подключений агентов); если он исчезнет, «из любого места» перестанет работать у всех
до обновления приложений. Телефоны детей теперь держат постоянное соединение каждый. Что делать: лимит
трафика на соединение, оповещения, настраиваемый адрес relay и короткая инструкция по своему серверу.

**S9. Что не закрыто на телефоне** (рассуждение; часть уже описана в документах): второй пользователь Android
или гостевой профиль, рабочий профиль и клоны приложений, браузерные игры, безопасный режим, а при
выключенном строгом режиме — «Очистить данные» или удаление, которые выглядят как «не в сети».

### Низкая

- **S10.** Запасной вход по паролю Windows (`LogonUser`) блокируется на 30 с после 3 ошибок, но только в
  памяти: перезапуск сбрасывает блокировку. Проходит ли учётная запись с пустым паролем, не проверялось.
- **S11.** `docs/SECURITY.md` называет обновления «подписанным релизом GitHub». Подписаны APK; установщик
  Windows подписи кода не имеет. Исправить текст или подписать установщик.
- **S12.** Детское приложение доверяет заголовку `Date` от relay через TLS. Проверить на устройстве, что
  установленный пользователем центр сертификации не принимается клиентом Ktor CIO (по умолчанию не должен).
- **S13.** Защита строгого режима — эвристика (имя приложения на экране настроек). Нужна проверка на
  телефонах разных производителей; возможны и пропуски, и ложные закрытия.
- **S14.** Файлы состояния лежат рядом с exe (`AppContext.BaseDirectory`), а не в папке данных пользователя.

### Проверено, замечаний нет

- **Noise.** Написан вручную на C# и Kotlin, но оба сверяются с опубликованными векторами (cacophony, snow) и
  друг с другом в CI; исчерпание счётчика, нулевой результат DH и размеры сообщений обработаны.
- **Подключение.** Одноразовый секрет в QR, вводимый 6-значный код, привязанный к рукопожатию, Windows Hello и
  обнаружение «код использовали два телефона». Проверка и запись идут в одной критической секции. Способа
  вклиниться второму телефону я не нашёл.
- **Сервер.** Два пути WebSocket, браузеры отклоняются, только адреса домашней сети, неизвестные ключи
  закрываются молча.
- **Устройство relay.** Он ничего не может прочитать или подделать; маршрут можно набрать, но нельзя
  зарегистрировать без секрета; агент держит свои лимиты, что бы ни прислал relay.
- **Android.** Наружу открыты только экран запуска и системные приёмники; резервные копии выключены; ключи
  запечатаны Keystore; родительский PIN — PBKDF2 с блокировкой, переживающей перезагрузку.
- **Ключ релиза.** Доступен только тегам `v*` через окружение GitHub (ты подтвердил настройку).

## Архитектура и корректность кода

**A1. У логики приложения Windows нет тестов.** Все 152 теста на C# покрывают протокол и relay. У
`TimerController` (657 строк), `ScheduleEvaluator`, `UsageTracker`, `ProtectedStore` и у связки запросов
протокола с таймером тестов нет. S1 и S2 — именно то, что такие тесты показали бы.

**A2. `MainWindow.xaml.cs` — 2578 строк кода в окне.** Моделей представления нет; состояние держат статические
помощники (`ProtectedStore`, `PasswordHelper`). Много блоков `catch { }`, глотающих ошибки: неудачное
сохранение настроек проходит молча. Это работает, но любое изменение там рискованно и не проверяется тестами.

**A3. Всё существует дважды, и копии разошлись.** Протокол реализован на C# и Kotlin (это оправданно: векторы
и тесты совместимости держат их вместе). *Правила* тоже реализованы дважды (`ScheduleEvaluator` /
`TimerController` и `ScheduleRules` / `PlayBackend`) и уже отличаются: защита от перевода часов, добавление
времени сверх расписания, события вмешательства и отложенные пуши есть только на стороне телефона. Варианты:
1. Оставить две кодовые базы, добавить общие векторы для правил (как для протокола). Самое дешёвое.
2. Перенести правила и протокол в одно ядро (Rust с `snow` или Kotlin/Native) с тонкими обвязками. Окупается,
   только если появится iOS или другие платформы.

**A4. `PlayBackend` (889 строк) сформирован правками по ревью.** Привязка дня с тремя уровнями доверия плюс
флаги `lift` / `auto` / `bonus` верны по тестам, но рассуждать о них трудно. Стоит выделить чистые «часы дня» и
«бюджет» и проверять их против простой эталонной модели случайными последовательностями действий.

**A5. Рост протокола.** Шесть младших версий (0–5) с v1.7.0 и спецификация на 789 строк. Согласование
возможностей и версий сделано хорошо. Часть про relay (пулы, вытеснение, смена маршрутов) тяжела для такого
числа пользователей, а каждое добавление стоит двух реализаций.

**A6. Нет пути обновления.** Ни приложение Windows, ни установленные вручную APK не узнают о новых версиях,
так что исправления безопасности сами ни до кого не доходят. Помогла бы проверка «доступна новая версия» по
релизам GitHub (небольшая уступка в приватности; сделать отключаемой).

**A7. Не видно, что происходит у пользователей.** Телеметрии нет по замыслу, поэтому сбои у пользователей
невидимы. Кнопка «выгрузить диагностику» сохранила бы подход к приватности и сделала бы поддержку возможной.

## Продукт, критически

**P1. Позиционирование.** Средства операционных систем (Microsoft Family Safety, Google Family Link, Apple
Screen Time) ограничивают внутри ОС и при сбое остаются закрытыми. Приложение в пользовательском режиме так
не может. Сильные стороны GameTimer в другом: без учётных записей и облака, работает с одной общей учётной
записью Windows, видимый ребёнку обратный отсчёт, одно родительское приложение для ПК и телефона, сквозное
шифрование, открытый код. Честная позиция — **прозрачный таймер для семьи, где есть договорённость**, а не
неснимаемый контроль. Это стоит прямо написать в README.

**P2. Модель угроз перевёрнута.** Посторонний в сети встречает криптографию банковского уровня. Ребёнок за
клавиатурой встречает файл, который можно удалить. Корень — решение D6 (одна общая учётная запись
администратора): почти все локальные находки выше следуют из него. «Известный пробел» из §11 протокола —
служба Windows плюс стандартная учётная запись ребёнка с родительским PIN в приложении — единственное
изменение, которое сделало бы ограничения на ПК настоящими.

**P3. Фаза C обещает больше, чем позволяет Android.** Без Device Owner агента можно удалить, очистить или
обойти, а направление развития Android (ограниченные настройки для приложений не из магазина, правила для
спецвозможностей, проверка разработчиков в 2027) работает против него. Варианты:
- пометить агента на телефоне в v2.0 как **бета** и описать его как инструмент для договорённости;
- для жёсткого контроля рекомендовать Family Link, а GameTimer Child оставить для общей картины и «попросить
  ещё времени»;
- предложить настройку Device Owner как расширенный вариант для отдельного детского устройства.

**P4. Две модели в голове.** На ПК таймер считает всё время и блокирует компьютер; на телефоне считает только
выбранные игры. Родитель видит оба в одном приложении. Либо добавить на ПК режим «только игры» (по активному
процессу), либо ясно показать разницу в приложении.

**P5. Пробелы по платформам.** Нет родительского приложения для iOS (у многих родителей iPhone), нет агента
для iOS, нет приставок. Общий модуль на Kotlin уже собирается под iOS, так что родительское приложение —
естественная следующая платформа.

**P6. Устойчивость.** Один сопровождающий; relay, Firebase и ключ подписи личные; кода не смотрел человек, и
внешнего аудита не было. Для семейного инструмента это нормально, но должно ограничивать публичные обещания.

## Что получилось хорошо

- Сначала спецификация, с независимыми тестовыми векторами и тестами совместимости C# ↔ Kotlin в CI.
- Независимое ревью на каждом PR каждый раз находило настоящие дефекты (пять проходов на C3, три на C4).
- Решения записаны с датами и причинами; позиция по приватности последовательна и описана.
- Гигиена релизов: ключ подписи доступен только тегам; перед релизом — кандидаты.

## Что поменять в процессе

- **Модель угроз до кода** для шагов, связанных с безопасностью. В C3–C4 проблему часов находили по одной
  лазейке за восемь проходов ревью; страница с моделью заранее нашла бы большую часть.
- **Обзоры всей системы на вехах**, а не только ревью изменений. Дыры на ПК (S1, S2) тянутся с v1.5–v1.6.
- **Проверка на устройствах на каждом шаге.** C2, C3 и C4 дошли до кандидата без единой сессии на устройстве.
- **PR поменьше.** C3 и C4 меняли примерно по тысяче строк логики безопасности за раз.
- **Ревьюер, отличающийся от автора** (другая модель или человек для рискованных частей).
